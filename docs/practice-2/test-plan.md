# Тестовый план СМП

## 1. Области тестирования

Проверяется вся СМП. Authorization и Card-Management покрываются классами эквивалентности, границами и двумя наборами PICT — [test-design.md](test-design.md). Для каждого другого сервиса есть отдельный раздел в [checklists.md](checklists.md).

Порядок прогона: подготовить карты и использованные суммы, выполнить дымовые проверки, проверить ядро и взаимодействие сервисов, провести сквозной платёж.

## 2. Критерии входа и выхода

**Вход в тестирование:**

- согласованы ТЗ и API-контракты;
- стенд Docker Compose запущен, дымовые проверки проходят;
- доступны PostgreSQL, RabbitMQ, логи и ответы API;
- подготовлены отдельные синтетические карты, зарегистрированные BIN и исходные суммы;
- можно задать статус, срок карты, баланс и записи limit_usage;
- для календарных границ можно управлять датой стенда, для отказов — отключать выбранную зависимость.

**Выход из тестирования:** выполнены все P1-кейсы и не менее 95% всего набора; все P1 проходят; нет открытых критических и высоких дефектов. Для оставшихся FAIL/BLOCKED записаны причина и влияние.

## 3. Техники тест-дизайна

- Классы эквивалентности: отдельные представители статусов, форматов и причин отказа; в негативном кейсе одно отказное условие.
- Граничные значения: точка на границе и соседние значения ниже/выше. Для денег шаг — 1 копейка.
- Попарное тестирование: сочетания параметров Authorization и Card-Management, сгенерированные PICT.
- Ручные дополнения: важные полные сценарии, например равенство суммы обоим остаткам лимитов и балансу.

## 5. Метрики покрытия

| Метрика | Как считать | Цель |
|---|---|---|
| Покрытие требований ядра | Требования с кейсами / требования в области | 100% |
| Покрытие классов | Классы с представителем и кейсом / выделенные классы | 100% |
| Покрытие границ | Описанные точки ON/OFF / запланированные точки | 100% |
| Покрытие пар | Покрытые допустимые пары / все допустимые пары модели | 100% для обеих моделей |
| Выполнение тестов | Выполненные кейсы / запланированные | 100% P1, не менее 95% всего набора |
| Успешность прогона | PASS / выполненные кейсы | Все P1 — PASS |
| Открытые дефекты | Количество по уровню серьёзности | Нет критических и высоких |

## 6. Приостановка и возобновление

| Приостановить | Возобновить |
|---|---|
| Ядро или БД недоступны, исходные данные нельзя подготовить | Восстановить зависимости, повторить дымовые проверки |
| Фоновые платежи меняют баланс и использованные суммы | Отключить генераторы, подготовить новые карты |
| Нет управления датой для календарного кейса | Подготовить управляемые часы стенда или тестовую подмену |
| Изменился контракт | Обновить кейсы и согласовать ожидания |
| Обнаружено неверное списание P1 | Проверить исправление на исходном кейсе и соседних границах |

## 7. Ресурсы

Ответственный за документацию и ручной прогон — Владимир Сорокин. Рецензирование — преподаватель и взаимная проверка по правилам курса.

Нужны Windows, PowerShell, Git, PICT, Docker Compose, PostgreSQL, RabbitMQ, REST-клиент и браузер. Перед каждым кейсом используется новая карта или восстановленные исходные данные. Непрерывная генерация платежей отключена.

Порты: Gateway 8080, CMS 8081, Switch 8082, Authorization 8083, Merchant + Acquirer 8084, Terminal 8085, Logger 8088, Bin Lookup 8096, Notification 8097, Dashboard 3000. Схема — в [architecture.md](../architecture.md).

## 8. Расписание

| Этап | Когда | Проверки |
|---|---|---|
| Модульные тесты | При изменении кода ядра | Правила лимитов, баланса, срока карты и Луна |
| Подготовка стенда | Перед прогоном API | Карты, статусы, баланс и исходный usage |
| Дымовые тесты | После сборки и запуска стенда | Доступность сервисов и зависимостей |
| API-тесты ядра | После успешных дымовых проверок | Классы, границы и кейсы PICT |
| Интеграционные тесты | После проверок API ядра | CMS, PostgreSQL, RabbitMQ и доставка событий |
| Сквозные тесты (E2E) | После интеграционных | Платёж от симулятора до журнала и Dashboard |
| Повторный прогон тестов | После исправлений | Исходный проблемный кейс и связанные проверки |

## 9. Риски

- Для INACTIVE/BLOCKED в ТЗ не указан отдельный код: обязательна причина отказа, код уточняется.
- Общие карты могут испортить соседний тест: использовать отдельные данные и отключать фоновые платежи.
- Случайный генератор неудобен для границ: нужные значения задавать явно.
- Журнал и уведомления обновляются асинхронно: поиск повторять до согласованного таймаута.
- Покрытие пар пропускает отдельные полные сценарии: добавлять важные комбинации вручную.
