# Практика 5. API-тесты СМП

Тесты находятся в `services/api-tests`. Стек: Java 21, JUnit 5, REST-assured 5.4.0,
Hamcrest 2.2, Awaitility 4.2.2, Jackson и JSON Schema Validator.
Прогон обращается к настоящим сервисам отдельного стенда Docker Compose.

## 2. Бизнес-отказы

Код и причина проверяются вместе. Карта для финансовых сценариев создаётся с балансом
1000, дневным лимитом 500, месячным 2000, статусом ACTIVE и валютой 643.

| Исход | Код | Подготовка и путь |
|---|---|---|
| CARD_NOT_FOUND | 14 | Несуществующая карта с известным BIN; неизвестный BIN; HTTP 400/404 CMS при чтении и резерве |
| CARD_BLOCKED | 05 | BLOCKED в карте; HTTP 402 CMS при чтении |
| CARD_INACTIVE | 05 | INACTIVE в карте |
| CARD_EXPIRED | 54 | Статус EXPIRED; дата платежа после последнего дня срока ACTIVE-карты |
| INSUFFICIENT_FUNDS | 51 | Сумма выше баланса; HTTP 402 при резерве |
| EXCEEDS_AMOUNT_LIMIT | 61 | Дневной лимит 499/500/501; остаток месячного лимита 199/200/201 на следующий день |
| SERVICE_UNAVAILABLE | 96 | Ошибки чтения CMS и резервирования; отдельно проверяется HTTP 503 внутреннего Authorization |
| RESERVATION_FAILED | 96 | HTTP 409 от резервирования CMS |
| UNKNOWN_REASON | 05 | CMS вернул карту с пустым статусом |
| DB_UNAVAILABLE | 96 | Ошибка сохранения слишком большого usage; проверка исходного ожидания выявляет D-10 |
| TRANSACTION_NOT_FOUND | 14 | Ошибка 400/404 от rollback CMS |
| ALREADY_ROLLED_BACK | 05 | Повторный rollback; HTTP 409 от CMS |
| ROLLBACK_FAILED | 96 | HTTP 422 от rollback CMS |

В `FaultApiTest` ответы зависимостей подменяет HTTP-прокси, а код Authorization и Switch
исполняется настоящий. Обычная оплата, резерв и возврат используют реальные карты.
При остановленном брокере отдельно проверяется ответ Switch `96 / System error`,
восстановление баланса и отсутствие поздней записи после восстановления доставки.

`ContractDefectsTest` сохраняет исходные ожидания. Его результаты лежат отдельно от

## 5. Обоснование достаточности

Основной набор содержит 481 сценарий. Разбиения взяты из DTO, валидаторов и обработчиков
ошибок; финансовые границы проверяются на отдельных картах. Для поиска используются
два заранее записанных сообщения с разными статусами и реквизитами.

Для CMS применён L8: 6 факторов, 8 строк, все 60 пар значений. Для поиска — L16:
9 факторов, 16 строк, все 144 пары. PAN или собственный BIN ограничивает выборку
данными теста. Отдельные сценарии проверяют действие каждого фильтра и пустой результат.
CSV проверяется по числу строк и PAN каждой строки с посторонней записью в хранилище.
Charts проверяет разные часовые/дневные корзины, исключение записи на верхней границе,
обратный диапазон и равенство границ. Recent проверяет созданные id в начале выдачи и сортировку всего ответа по createdAt DESC.

Для асинхронной доставки используется Awaitility: появление записи — до 10 секунд,
опрос раз в 100 мс. После отказа публикации и восстановления брокера сначала проходит
контрольная оплата с доставкой в журнал, затем 10 секунд проверяется отсутствие
неудачного платежа. Для восстановления контрольная оплата ожидается до 45 секунд;
каждая попытка использует новую карту, затем отдельно ожидается её доставка в журнал.
Исходный неудачный платёж повторно не отправляется. SQL-запросов и чтения очередей в тестах нет.

Ограничения: недетерминированная коллизия генерируемого PAN и исчерпание повторов
создания карты не воспроизводятся. Все варианты внутренних 500, нагрузка, WebSocket,
UI и проверка протоколов PostgreSQL/RabbitMQ требуют отдельных прогонов.
Баланс после отката проверяется через HTTP; компенсация usage
не доказана этим набором. Административные Actuator/Swagger-эндпоинты вне матрицы.

Стенд использует девять Java-сервисов, два PostgreSQL и RabbitMQ, порты привязаны
к localhost. Logger разрешает десериализацию сообщений своего изолированного брокера;
без этой настройки сообщение Switch отвергается. Лимит Gateway уменьшен до 2 запросов
без пополнения для проверки 429, каждому обычному тесту назначается собственный IP.
Карты симуляторов выбираются через HTTP-подмену из собственных данных теста.

Logger использует отдельный PostgreSQL с сохраняемым томом. Аварийная группа готовит
сообщение через HTTP, отключает эту БД и проверяет 503 при записи и пяти операциях чтения
(чтение также через Gateway). После восстановления проверяются прежняя запись и новая запись.
Сами тесты не обращаются к SQL. Полный набор состоит из 13 проверок подготовки, отказа и восстановления.

`known-contract-failures.json` хранит рассмотренные имена и причины 19 контрактных падений.
Скрипт сверяет состав группы и текст каждого assertion. Новый отказ, техническая ошибка,
пропуск или неожиданное прохождение известного дефекта завершают запуск с ошибкой.

## 7. Порядок запуска

Нужны JDK 21, Maven, PowerShell 7 и работающий Docker Desktop. Из корня репозитория:

```powershell
pwsh -File ./scripts/run-api-tests.ps1
```

Команда собирает сервисы, поднимает отдельный стенд, выполняет три основных прогона,
проверку отказа брокера, мутации, проверки дефектов и отключение/восстановление БД Logger,
затем удаляет тестовые контейнеры и том тестовой БД.
Отчёты JUnit находятся в `services/api-tests/target/reports/`, логи — в `target/evidence/`.
Workflow `Practice 5 API tests` запускает эту же команду и сохраняет результаты
в артефакт `practice-5-api-results`.
